1 · Overview

The pieces

Awase is a pull system, like a mining pool or BOINC. Volunteers' clients ask the orchestrator for work. The orchestrator never connects to a volunteer's machine, so volunteers need no open ports and no fixed address.

Watcher

Follows RenkuOSPorts main, by a webhook and a poll every five minutes in case the webhook is missed. Only merged commits count, so no pull request ever reaches a volunteer.

Planner

Turns a new commit into jobs, one per port and platform, with HaikuPorter's --ports-for-files, the logic the arm64 runner's update-packages.sh uses today. It also reads each port's dependencies, so jobs form a graph.

Scheduler

Answers clients' requests for work: picks a job the client can build, and leases one copy of it to the client. Section 5 covers how it chooses.

Validator

Checks each signed result against the client's key, and compares the two results of a job. A package whose two builds match is accepted, which can make its dependents buildable.

Assembler

Runs package_repo over the accepted packages to make a candidate repository. It's a CI job, not part of the server. It compiles nothing and holds no secrets.

Key holder

A person, not a service. They rebuild the candidate on their own machine, check it gives the same repo.sha256, and sign it. The key never touches the orchestrator.

  loop every 60 s while building
    A->>O: heartbeat (step, progress)

  A->>S: upload hpkg (by sha256)

A mismatch sends the job back to ready, with both results and logs kept for a maintainer. An expired lease frees its copy for another client.

3 · Deployment

Deploying the orchestrator

The orchestrator is meant to be small enough that one modest server runs it, and boring enough that anyone with the repository can rebuild it.

PartWhatWhy
ServiceOne process serving the client API, the scheduler and the validator, built as a container image in this repository's CI.One thing to run, update and watch.
StateSQLite in WAL mode, streamed to object storage with Litestream.The state is small: jobs, leases and results for one ports tree. No database server to run.
Packages and logsS3-compatible object storage, with keys named by sha256.Clients upload straight to storage with a short-lived URL, so large files never pass through the service.
TLS and routingCaddy in front, with automatic certificates.HTTPS with no manual renewals.
HostOne VM with 2 vCPUs, 4 GB of memory and 40 GB of disk. To start with it could be the server that hosts renkuos.freemyip.com, then later an EU host, as charter §6 suggests.The orchestrator does no building, so it needs little.

How a change reaches the server

  1. A pull request changes the service, its configuration in deploy/, or a platform file, and is reviewed like any other change.
  2. A merge to main builds and tests the container image in CI and publishes it to the GitHub container registry, tagged with the commit.
  3. A release tag deploys it. The deploy job waits for a maintainer's approval in a protected GitHub environment, then runs docker compose pull && docker compose up -d on the server over SSH.
  4. Rolling back means deploying the previous tag. The database schema only ever grows (new tables and columns, never a destructive change), so an older image still reads it.
# deploy/compose.yaml (sketch)
services:
  awase:
    image: ghcr.io/idumych/awase-orchestrator:${TAG}
    env_file: /etc/awase/orchestrator.env   # storage keys, invitation secret
    volumes: [ "state:/var/lib/awase" ]
  litestream:
    image: litestream/litestream:0.3
    command: replicate
    volumes: [ "state:/var/lib/awase", "./litestream.yml:/etc/litestream.yml:ro" ]
  caddy:
    image: caddy:2
    ports: [ "80:80", "443:443" ]
    volumes: [ "./Caddyfile:/etc/caddy/Caddyfile:ro", "caddy:/data" ]
volumes: { state: {}, caddy: {} }

What the server holds, and what it doesn't

On the server

  • Storage credentials, to sign upload and download URLs
  • The secret that invitation codes are checked against
  • Clients' public keys
  • The job queue, leases and results

Never on the server

  • The repository signing key
  • Clients' private keys
  • Any compiler or build guest. It runs no build code.

If the server is lost, a new one is set up from deploy/, its database is restored from Litestream, and the watcher replays RenkuOSPorts from the last commit it processed. Results are signed by the clients and the packages are in storage, so nothing that was accepted needs building again.

4 · Platforms

Platform definitions

A platform is what a package is built for. A host type is a kind of machine that can build for it. Both are plain files in git, so adding an architecture or a new guest image is a reviewed pull request.

A platform file

# platforms/x86_64.yaml
name: x86_64
tier: 1                         # D4: Tier 1 blocks releases
haikuporter:
  target: x86_64                # HaikuPorter's TARGET_ARCHITECTURE
  secondary: []                 # x86_gcc2h: target x86_gcc2, secondary [x86]
  revision: 1a2b3c4             # pinned HaikuPorter commit
guest:
  image: https://…/awase-guest-x86_64-hrev59210.raw.zst
  sha256: 77ae…                 # every copy of a job uses exactly this image
  network: none
inputs:
  repository: renkuosports-x86_64   # build packages come from accepted packages
quorum: 2                       # matching builds needed to accept a package
quorum_overrides:               # stricter for the toolchain and crypto
  gcc: 3
  binutils: 3
  openssl3: 3
single_build: []                # ports accepted from one build plus a maintainer
host_types: [linux-kvm-x86_64, renku-x86_64]

Host types

# host-types/linux-kvm-x86_64.yaml
name: linux-kvm-x86_64
runs: qemu-system-x86_64 -accel kvm
builds: [x86_64, x86_gcc2h]
speed_factor: 1.0               # emulation would be ~0.05
needs: { kvm: true }

# host-types/linux-tcg-arm64.yaml
name: linux-tcg-arm64
runs: qemu-system-aarch64 -accel tcg
builds: [arm64]
speed_factor: 0.06
needs: { opt_in: long_jobs }

When a client enrolls, it reports what it can run: KVM or not, its architecture, cores, memory and free disk. The orchestrator works out its host types from that. The client checks the guest image's sha256 before every build, so all copies of a job run in identical guests. That's what lets two builds match.

5 · Scheduling

Scheduling

Scheduling happens when a client asks for work. The scheduler doesn't plan the whole queue ahead: it answers one request at a time, in a few milliseconds, from the jobs that request can take.

Which jobs a client can take

  • Ready: every build dependency of the job is accepted.
  • Buildable: one of the client's host types builds the job's platform.
  • Fits: the job's estimated peak memory and disk fit the client's limits, and its estimated duration on that client fits the longest job the volunteer accepts.
  • Not already its own: the client doesn't hold or hasn't returned the other copy, and doesn't share an owner with whoever does.

Which of those it gets

The eligible jobs are ranked by these rules, in order:

  1. Security fixes first: a recipe change marked as a security fix jumps the queue.
  2. Second copies before first copies: a job with one result waiting is closest to being accepted. Finishing it frees its dependents sooner, and the first result doesn't go stale.
  3. Most blocked work first: jobs are ranked by how much work waits on them, which is the sum of the estimated costs of everything that depends on them, directly or not. That's why gcc and glib2 go before mpv.
  4. Size to the machine: among jobs close in rank, a slow or limited client gets the shorter jobs and a big one the longer ones, so a laptop never holds up the toolchain.
  5. Oldest first breaks any remaining tie.

Estimates

A job's cost comes from the last accepted build of that port on that platform: the median duration, in "reference seconds", plus peak memory and disk. A port with no history gets a conservative default for its platform. Each client has a speed: the ratio of its actual times to the estimates over its last 20 builds, starting from a two-minute calibration build at enrollment. A job's expected duration on a client is cost ÷ speed.

Leases

RuleStarting value
Heartbeat interval60 s, with the build step and progress
A lease is lost after5 missed heartbeats, or its deadline
Deadline2 × the expected duration + 1 h
A paused clientkeeps its lease while it sends heartbeats, up to the deadline
A late resultis still used if the job needs it, otherwise counted for credit and dropped
Leases per clientone per slot. A client with many cores can ask for two slots.

Inputs and snapshots

A lease names the snapshot of accepted packages to build against, by its sha256. Both copies of a job use the same snapshot, even if more packages are accepted in between. Otherwise the two builds would start from different inputs and couldn't be expected to match.

What triggers rebuilds

  • A recipe changes on main: that port, as now. As in HaikuPorts, dependents are rebuilt only when their own recipes change. This is the usual practice, and Awase doesn't change it.
  • A builder's key is revoked: every package that key helped accept goes back to one result, and the copy is scheduled again.
  • A platform file changes its guest image or HaikuPorter revision: nothing is rebuilt automatically. The change applies to new jobs, and a maintainer can queue a full rebuild.

Publishing

The assembler makes a candidate repository when the queue for a platform drains, or every 24 hours if it doesn't. A key holder signs it, and the download server only switches to a correctly signed repository.

6 · Failure

When things go wrong

What failsWhat happens
The orchestrator is downClients finish their current builds, keep the results, and retry with backoff, up to an hour between tries. Users' installs aren't affected, because the download server is separate.
A client vanishes mid-buildIts lease expires and the copy goes to someone else.
Two builds disagreeThe job goes back to ready, and the pair's logs and packages are kept for a maintainer. A port that mismatches three times is held until a maintainer looks.
A client keeps disagreeing with othersIts new leases stop after three mismatches in a week where the other side agreed with a third build, and a maintainer is told.
Storage is lostPackages can be fetched again from the download server and mirrors. Logs are lost, but they aren't needed to trust anything.

7 · Open

Open questions

  • Whether HaikuPorter builds are bit-for-bit reproducible. Phase 0 measures it, and the answer decides how long the single-build lists start out.
  • Whether a Renku-native build (HaikuPorter's chroot) and a build in the Linux guest of the same image can match, or whether they need separate platforms.
  • Who runs the orchestrator and holds its server's keys, and who holds the release key (D2).
  • Building a small orchestrator of our own, or trying BOINC first, as the proposal asks.
