How Awase runs

The pool runs on Dru's RenkuOSPorts portal: a public package repository and build coordinator for Renku OS, which now does the two-build check Awase proposed. This page follows the portal's code as of commit 56dde86. Awase is one of its build clients. Where a number appears, it's the portal's default setting.

1 · Overview

The pieces

The pool is a pull system, like a mining pool. Build clients ask the portal for work over HTTPS; the portal never connects to a volunteer's machine, so volunteers need no open ports and no fixed address.

Recipe sync

Reads the RenkuOSPorts tree (a mounted checkout, or a git clone it fetches and hard-resets to the branch tip) and records every recipe with its date. Admins queue jobs for recipes and platforms.

Automatic updates

Off by default. Every few hours (6 by default) it looks at what changed in RenkuOSPorts since the last run and queues the new version of each changed port on platforms that already publish it.

Build priorities

Evaluates every recipe per platform the way HaikuPorter does, builds the dependency graph, and gives each port a priority: how many outstanding ports need it.

Client API

What build clients call: a token from the client's ID and secret, the next job, uploads, complete, fail and release. Plus read-only views of the queue and of the client itself.

Verifier

Runs after every completed build and every 10 seconds. It compares the job's builds and publishes, queues another build, waits for an admin, or fails the job.

Repository indexer

Checks each published package with Haiku's package tool and builds the platform's pkgman repository with package_repo.

A job's life

sequenceDiagram
  participant G as RenkuOSPorts
  participant P as Portal
  participant A as Client A
  participant B as Client B
  G->>P: recipe changed (sync or automatic update)
  P->>P: queue zlib 1.3.1 for x86_64
  A->>P: POST /api/client/jobs/next

  A->>A: build command: zlib 1.3.1 outdir
  A->>P: POST …/packages (sha256, buildDate, file)
  A->>P: POST …/complete (log)
  P->>P: Verifying: one build, queue the next
  B->>P: POST /api/client/jobs/next
  P-->>B: zlib 1.3.1, build 2
  B->>P: packages, then complete
  P->>P: contents match: publish, rebuild the pkgman index
Queued→ InProgress→ Verifying→ Queued for the next build→ Succeeded

A job can also become AwaitingOverride (builds differ only in dates), Failed or Cancelled. Each claim is a build of its own: InProgress, then Completed, Failed, Expired (the lease ran out or the client gave it back) or Discarded.

3 · Verification

The two-build check

Every job is built twice and published only when both builds have the same contents. Uploads are staged for their build; they become public packages only when the job is approved. Packages imported by an admin, and those published before verification existed, are trusted as they are.

What "the same" means

HaikuPorter builds aren't reproducible byte for byte: every hpkg records file times. So the portal compares contents. For each of the port's packages it takes the metadata (package list -i, without any field about dates or times), every entry's path, type, permissions, size, symlink target and attribute names (package list -a, without the time column), and the SHA-256 of every extracted file, and hashes them into a content digest. Two builds match when their digests are equal. A file the package tool can't read is compared byte for byte.

Independence

When a client completes a build, only other clients may claim the job's next build, for as long as that build took. After that, any client may, the first one included. A job whose matching builds came from one client is published as self-verified; one whose builds came from two clients shows "verified: 2 clients".

BuildsWhat happens
Two matchPublished: the earliest matching build's packages. The other builds' staged files are deleted.
Two differA third build is queued. Whichever result two builds agree on is published.
Three all differThe job fails and the admins are emailed.
Differ only in datesEvery difference is a short run inside a date or time, at the same size on both sides. The job waits for an admin, who can approve a build and must give a reason. Who, when, why and which build are recorded, and the package shows as overridden. A port flagged as embedding dates is approved automatically from then on.
A build failsThe job fails, as a failed build always did, and every build's staged files are deleted.

Extras

A build sometimes makes packages of other ports on the way, dependencies it needed. They are recorded as extras and not published, and their bytes aren't kept. A package belongs to the port when its name is the port's or starts with <port>_, unless a longer port name claims it.

Setting: Verification:RequiredMatches, 2 by default. 1 publishes the first build, with no check.

4 · Scheduling

Scheduling

A client asks for work and gets one job, claimed in a single SQL transaction: two clients never take the same build, and a client still inside its window for a job skips it.

Which job a client gets

  1. Its platform: a client builds for the one platform it was registered with: x86, x86_64, arm64 or riscv64.
  2. Most blocked work first: the port with the highest build priority, the number of outstanding ports that need it, directly or through other outstanding ports. That's why the toolchain goes before an app.
  3. Oldest first among equal priorities, then the lowest job number.

Priorities are recomputed at startup, after each recipe sync, five minutes after a package is published or deleted, and on request. Admins can also queue the top 20 outstanding ports of a platform in one go.

Leases and giving back

RuleValue
Lease72 hours from the claim (Jobs:LeaseHours)
An expired leaseis found at the next claim. Only that build goes back to the queue; completed builds keep counting. The admins are emailed.
Giving a job backPOST …/release with a reason: the job is queued again at once, with no email, and the reason is kept as "Released: …". Awase does this when you quit mid-build.
A late reportfrom a client whose lease expired gets 409, or 403 if another client holds the job now.
The queueClients can read it with their own token: what's queued and building, their place in it, and what each job waits on.

5 · Clients

The clients

Every client speaks the same API. Most run a build command, under the same contract:

<build command> <port> <version> <outdir>
  RENKUPORTS_PLATFORM     the job's platform
  RENKUPORTS_JOB_ID       the job
  RENKUPORTS_RECIPE_PATH  the recipe in the ports tree
  RENKUPORTS_PORTS_URL    the ports repository the portal builds from (Awase, container clients)
  RENKUPORTS_PORTS_REF    its branch
  AWASE_CORES             the cores lent (Awase)
# exit 0 and leave the *.hpkg files in <outdir>; anything else fails the job
ClientWhereHow it builds
AwaseRenku OS, nativeA build command, within the limits you set: when idle or always, cores lent, pause and resume.
awase-tuiLinux serversThe same core as Awase in a terminal, or plain log lines under systemd.
RenkuPorts BuilderRenku OS, nativeHaikuPorter in a local ports tree, which it clones and updates itself.
Linux and macOS appsGTK4, SwiftUIA container that boots a Renku guest under QEMU and runs HaikuPorter inside it, for any platform.
renkuports-clientAnywhere with .NET 10A build command. Also prints the queue.

Awase uploads every package with its SHA-256 and the file's time as the build date, completes the build with the last 5 MB of the log, and fails the job with a reason when the command fails or makes nothing. A local problem, like a build command that won't start, gives the job back instead, and Awase waits before asking again.

On the server

  • Accounts, with optional GitHub sign-in
  • Build clients' secrets, stored only as hashes
  • The job queue, builds and their differences
  • Staged and published packages and logs

Not yet

  • Clients' signing keys and signed builds
  • A repository signed offline by a person
  • Matching builds required from two different people

7 · Failure

When things go wrong

What failsWhat happens
The portal is downAwase keeps retrying with backoff, up to five minutes between tries, and finishes the build it has.
A client vanishes mid-buildIts lease expires after 72 hours and the build goes back to the queue. A client that quits properly gives it back at once.
The build failsThe job fails with the client's reason and log, and the admins are emailed. An admin can queue it again.
Two builds disagreeA third build decides. If all three differ, the job fails. Differences only in dates wait for an admin.
An upload is corruptedIts bytes don't match the SHA-256 sent first, and it's refused.
A package is rebuilt without a new revisionA published file is never replaced: an upload with the same name and different contents is refused.

8 · Then and now

From the proposal

The original proposal described a pool server of its own. The portal took its place. The core idea carried over, and some parts changed when they met real builds.

PartThe proposalThe portal
The checkTwo builds with the same sha256Two builds with the same contents, since HaikuPorter records file times
IndependenceTwo builders with different ownersA different client preferred; self-verified packages are marked
MismatchesSent to a maintainerA third build decides; date-only differences go to an admin
SchedulingMost blocked work firstThe same idea: build priority from the dependency graph
JoiningAn invitation code from a maintainerSign in and register a client
ServerOne small service with SQLiteASP.NET Core with SQL Server and blob storage, aimed at Azure
BuildsA sealed guest with no networkThe client's choice: HaikuPorter on Renku, a QEMU guest in a container, or any build command
SigningSigned results and an offline-signed repositoryNot yet: SHA-256s are checked, nothing is signed

Open questions

  • How builds and the repository get signed, and who holds the release key: suggested in the portal's issue #2.
  • Whether matching builds should come from two different people, not just two clients.
  • Whether a native Renku build and a build in a QEMU guest of the same image match, or need separate platforms.
  • Who hosts the portal in public.
